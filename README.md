# Saajha — VRPPD/VRPTW Matching Engine

Reference implementation of the core matching algorithm behind **Saajha**,
our submission to the GAVS Hackathon, Problem Statement 5.3 ("Rural freight
moves half-empty, late and at high cost", Applied AI Systems track).

This repository contains the optimizer that pools nearby farmers'/traders'
shipments into shared trips and matches shipments onto a transporter's
**return leg** wherever possible, modelled as a **Vehicle Routing Problem
with Pickup and Delivery, Capacity Constraints and Time Windows
(VRPPD/VRPTW)**, benchmarked against a simple greedy baseline as the
hackathon brief requires.

## How this maps to the hackathon brief

| Brief requirement | Where it's handled |
|---|---|
| Every shipper sharing a vehicle can see how their price was calculated | `src/fare_splitter.py` |
| Transporters accept/reject loads voluntarily | Not a solver constraint — this repo produces *proposed* matches for a transporter to accept or decline at the product layer; see the main submission for that flow |
| The solution accounts for uncertain demand | `solve()` is designed to be re-run on a short rolling window every time new data arrives, rather than forecasting — see "Handling uncertain demand" below |
| Optimization is benchmarked against a simple baseline | `src/benchmark.py`, comparing `vrppd_solver.py` against `baseline_matcher.py` |
| Quantum hardware is optional | Not used — see "On quantum-inspired optimization" below |

## Run the demo

```bash
python -m demo.run_demo
```

This runs two synthetic scenarios — a sparse-demand corridor and a dense,
harvest-season-like corridor — through both the baseline matcher and the
VRPPD/VRPTW optimizer, prints a side-by-side comparison (matched shipments,
total cost, vehicles used, load factor, return-leg matches), and prints one
live, itemised fare breakdown for a pooled trip.

**All numbers produced by this demo are from synthetic data**, generated by
`src/data_generator.py` with a fixed random seed for reproducibility. They
illustrate the mechanism, not a measured real-world result — see the
"Expected Impact" section of the main hackathon submission for how we would
measure this with real or pilot-corridor data.

## Run the tests

pip install pytest     # optional; plain `python3 tests/test_basic.py` also works

## How the algorithm works

1. **Nodes.** Every shipment contributes a pickup node and a delivery node.
   Every vehicle gets its own start node at its current location. A single
   shared, zero-cost "end depot" node lets every vehicle's route stay open —
   a vehicle does not have to drive back to its own start to finish its
   route.
2. **Capacity.** A capacity dimension tracks each vehicle's running load:
   `+weight` at a pickup, `-weight` at a delivery, bounded by the vehicle's
   `capacity_kg` at every point on the route.
3. **Time windows.** Each pickup and delivery has an allowed time window;
   each vehicle has a shift window. The solver respects both and allows a
   vehicle to wait if it arrives early.
4. **Pickup-delivery pairing.** `AddPickupAndDelivery` plus two extra
   constraints (same vehicle, pickup-before-delivery) keep each shipment's
   two stops together and in the right order.
5. **Cost.** Every vehicle has its own cost-per-kilometre. A **return-leg**
   vehicle (`is_return_leg=True`, i.e. "recovered" capacity on a trip that
   was going to happen anyway) is costed at a discount — this is how
   KhaliVapsi-style backhaul matching is represented inside the same solver
   as ordinary outbound pooling, rather than as a separate system. A fixed
   cost per vehicle used rewards the solver for pooling shipments onto fewer
   vehicles instead of spreading them out.
6. **Benchmark.** `src/benchmark.py` runs the same scenario through
   `baseline_matcher.py` — one shipment, one vehicle, no pooling, full price
   — and reports the difference, so any claimed improvement is measured,
   not assumed.

## Handling uncertain demand

This repository does **not** try to forecast demand. `solve()` solves one
batch of currently-known shipments and currently-known vehicle capacity. In
the full system, this function is called again on a short rolling window
every time a new shipment is posted, new vehicle capacity becomes available,
or a transporter cancels — which is how the product stays usable under
genuinely uncertain, spiky (harvest-driven) demand without depending on a
prediction that could be wrong.

## On quantum-inspired optimization

The brief allows classical or quantum-inspired optimization, with quantum
hardware explicitly optional. We use a classical solver (OR-Tools) because
the instance sizes on a single village-to-mandi corridor don't need more
than that, and the brief's actual requirement — a fair benchmark against a
simple baseline — is satisfied by `benchmark.py` regardless of which solver
sits on the optimized side. A quantum-inspired solver could be added
alongside the classical one for an explicit, honest comparison once there is
real traffic data to test it against; see "Future Potential" in the main
submission.

## Known simplifications (hackathon-stage, documented honestly)

- Shipments are assumed to be jointly feasible for the given vehicles and
  time windows; the data generator is tuned to keep instances solvable. A
  production version would add bounded disjunctions so one hard-to-place
  shipment can be left unmatched, with a penalty, rather than the whole
  batch failing to solve.
- Distance is computed with the haversine (straight-line) formula, not real
  road distance. Swapping in OSRM (OpenStreetMap routing) is a drop-in
  replacement for `haversine_km` in `src/models.py`.
- The Fare Explainer's "detour cost" removes a shipment's two stops from the
  route and re-measures it, without re-optimising the order of the
  remaining stops. This is a reasonable, explainable approximation for a
  prototype, not an exact marginal-cost calculation.
- This repository produces proposed matches; it does not implement the
  transporter accept/reject interface or the cancellation re-match trigger
  described in the main submission — those are product-layer concerns, not
  part of this algorithm.
- This code was written and syntax-checked in an environment without
  internet access, so the OR-Tools solver path (`vrppd_solver.py`) has not
  been executed end-to-end by us; everything that doesn't require OR-Tools
  (`models.py`, `data_generator.py`, `baseline_matcher.py`,
  `fare_splitter.py`) has been run and its tests pass. Run `pytest tests/ -v`
  after `pip install -r requirements.txt` to confirm the solver on your own
  machine before demo day.
